# Overview

This gem has **no hand-written resource code**. Every namespace, method, and
parameter signature is generated at load time from `lib/elevenlabs/spec.json`,
and that file is generated by `scripts/extract_spec.py` from the vendored
upstream SDK in `tmp-elevenlabs-python/src/elevenlabs/`. Adding support for a
new ElevenLabs endpoint is therefore a *regeneration*, not an implementation —
the consuming half of that spec is described in
[the dynamic resource graph](/runtime/dynamic-resource-graph.md).

The non-obvious part is **how** the extractor reads the Python source. It does
not import the SDK and it does not read OpenAPI. It parses each `raw_client.py`
method with `ast`, finds the `self._client_wrapper.httpx_client.request(...)`
call, and then **evaluates the call's argument expressions** with `eval` under a
controlled globals dict (`EVAL_GLOBALS`), with parameter names bound to
placeholder strings. What survives that evaluation — the path template, the
query entry list, the JSON body shape, the file entries — becomes the operation
spec.

That design is why the extractor is resilient to formatting changes upstream but
fragile against *new helper functions*: any name it has never heard of degrades
into a placeholder, which is the failure mode documented in
[the extractor's Dummy trap](/generation/extractor-dummy-trap.md).

# What the spec records

| Spec key | Meaning |
|----------|---------|
| `children` | Nested namespaces, keyed by accessor name (`conversational_ai`, `workspace`, …) |
| `operations` | Callable methods on that node |
| `request.method` / `request.path` | HTTP verb, plus a `{param}` template and its param list |
| `request.query` | Ordered entries, each either a `param` reference or a `literal` |
| `request.json` / `request.form` | Body `literal` seed plus `assignments` (param → path within the body) |
| `request.files` | Multipart entries (`param`, `literal`, `tuple`, `list`) |
| `request.streaming` | Routes the call to `HTTPClient#stream` instead of `#request` |
| `positional_params` / `keyword_params` | The generated Ruby signature, with `__OMIT__` marking the sentinel default |

# Boundaries

`spec.json` records **operation signatures only**. It deliberately does not
carry the nested shape of Pydantic-typed parameters such as `workflow` or
`conversation_config` — those come from a second, independent pass described in
[type extraction](/generation/type-extraction.md). Keeping the two passes
separate is what lets the request layer treat those parameters as opaque hashes
while callers still get a machine-readable schema.

Regenerating this file is step 2 of [the update procedure](/release/update-procedure.md).
